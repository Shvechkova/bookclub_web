# Design

## Context

Итоги встречи сейчас — `Outcome` из трёх строк и цитаты. Их показывают две
страницы: «Сейчас» (только три тезиса) и страница встречи. Картинки на сайте
есть только у книг: путь внутри `app/web/static`, файл лежит в `static/covers/`
и выгружается в статику вместе со всей папкой. Карточка пересылки
(`og:image` в `base.html`) на всех страницах одна — логотип.

Источник наполнения — заметки клуба в Obsidian:
`Книжный клуб/10_итоги_встреч.md` (тексты итогов, как ушли в канал) и
`Книжный клуб/anons-brooks/` (посты анонсов, афиши `a-afisha*.png`, карточки
итогов `i-*.png` и др.). Все картинки 2160×2700, от 0,2 до 5 МБ.

## Goals / Non-Goals

**Goals:**
- Итоги на странице встречи читаются так же полно, как пост в канале.
- Одна картинка на встречу в нужный момент: афиша до, карточка итогов после.
- Наполнить две прошедшие встречи по Бруксу и афишу третьей.

**Non-Goals:**
- Галерея из всех карточек серии (`o-*`, `m-*`, `i-spor`, `i-shtamp`): решено
  ограничиться основной карточкой.
- Перенос полного текста поста как есть, с эмодзи и обращениями к каналу.
- Автоматический импорт из Obsidian. Заметки переносятся руками, один раз.
- Итоги встречи 21.10: их нет в заметках.

## Decisions

### Полная форма итогов — поля того же `Outcome`, а не новая сущность

К `Outcome` добавляются необязательные поля:

```yaml
outcome:
  agreed: …            # как раньше: три тезиса для «Сейчас»
  argued: …
  taken: …
  quote: { text: …, chapter: 15 }
  lead: …              # вступление, абзац
  by_chapter:          # «О чём говорили по главам»
    - { chapters: [8], heading: Оценка сроков, text: … }
    - { heading: Бюджеты, text: … }          # без глав
    - { chapters: [6, 7], text: … }          # без заголовка
  debates:             # «Главные споры»
    - { heading: Блок-схемы, text: … }
  aside: …             # «Заодно уходили в…», строкой
  verdict: …           # общий итог, абзац
```

`OutcomeItem(heading: str | None, text: str, chapters: tuple[int, ...])` служит
и для пунктов по главам, и для споров. У спора номера глав тоже допустимы, в
посте они просто не стоят. `Outcome.is_empty` учитывает новые поля, иначе
итоги только из полной формы молча пропадут.

Почему не отдельная `Recap` рядом с `Outcome`: это одни и те же итоги, и две
сущности пришлось бы держать согласованными, например решать, что показывать,
когда заполнена только одна из них. Почему не одно поле markdown: сайт не
хранит текстов разметки, а пункты с номерами глав нужно проверять по книге и
показывать номером в стиле `.num`.

Номера глав в пунктах проверяются той же функцией, что и `chapters` встречи:
глава должна существовать в книге встречи, а у встречи без книги номеров быть
не может.

### Картинки — два поля встречи с обязательной подписью

```yaml
images:
  poster: { src: meetings/m-2026-10-21-poster.jpg, alt: … }
  recap:  { src: meetings/m-2026-10-07-recap.jpg,  alt: … }
```

`MeetingImage(src, alt)`, `Meeting.poster` и `Meeting.recap_card`. Какую
картинку показывать, решает функция ядра от встречи и «сегодня» (в
`app.core.view`, рядом с `is_past`), а не шаблон: правило проверяется тестом
ядра без вёрстки.

Почему подпись обязательна, когда у обложки она собирается сама: на афише и
карточке текст, которого нет больше нигде на странице, например цитата вечера
крупно. Сгенерированная подпись «афиша встречи #5» его не передаёт.

Альтернатива — список картинок с ролями — отвергнута: ролей ровно две, а
правило выбора с ними проще.

### Файлы — уменьшенные JPEG в `static/meetings/`, ужатые один раз

Исходники переносятся в `app/web/static/meetings/<id встречи>-{poster,recap}.jpg`,
по ширине 1080 (1080×1350, 4:5), JPEG с качеством около 85. Целевой вес до
300 КБ. Для пересылки 1080 по ширине хватает с запасом, а телеграм всё равно
пережимает. Ужимает одноразовый скрипт в папке для черновиков, проекту Pillow
не нужен. Выгрузка уже копирует `static/` целиком, менять её не надо.

Почему не WebP: телеграм и часть мессенджеров хуже берут WebP в `og:image`.
Почему не держать исходник рядом: 5 МБ на страницу при показе в 760 точек.

На странице картинка обёрнута ссылкой на сам файл (это и есть «полный размер»),
`loading="lazy"`, `width`/`height` заданы, чтобы раскладка не прыгала, по
ширине `max-width: 100%`.

### Карточка пересылки

`base.html` получает блок `og_image` со значением по умолчанию — логотип.
`meeting.html` переопределяет его картинкой встречи через тот же `absolute()`.
Без `SITE_URL` абсолютных адресов нет, как и сейчас.

### Наполнение

- Тексты берутся из раздела «Текст из канала» в `10_итоги_встреч.md`: это
  версия после humanizer-ru. Эмодзи-маркеры пунктов и обращения к каналу
  («Приходите 🙌», «Спасибо всем, кто пришёл!», анонс следующей встречи)
  отбрасываются.
- Имена участников в текстах заменяются безличными формулировками: сайт
  индексируется, а модель не хранит данных участников. Так сделано и на
  карточке `i-itogi`. Ведущая 07.10 ставится в поле `host`, раз оно для этого и
  есть.
- Три тезиса собираются из уже написанного в посте и не придумываются:
  согласились — общий знаменатель, спорили — главный спор, забираем — вывод
  одного из пунктов.
- Разобранные главы 23.09 (1–7) и 07.10 (8–15) получают `outcome: closed`: оба
  поста и штамп «главы 8–15 закрыты» это подтверждают. Главы 21.10 остаются без
  отметки, пока нет итогов.
- Темы — понятия, которые прямо названы в постах: закон Брукса, эффект второй
  системы, закон Конвея, ADR, регрессионное тестирование и т. п.
- Картинки: 23.09 — афиша `a-afisha.png`; 07.10 — афиша `a-afisha-2.png` и
  карточка `i-itogi.png`; 21.10 — афиша `a-afisha-3.png`.

## Risks / Trade-offs

- [Посты в канале и сайт разойдутся, если пост поправят после переноса] → на
  сайт идёт версия после humanizer, она же финальная в канале; источник
  записывается в описании изменения.
- [Безличные формулировки звучат суше поста] → правятся только места с именами,
  остальной текст переносится как есть.
- [Картинка 1080 мутнеет при увеличении на большом мониторе] → по нажатию
  открывается тот же файл; если не хватит, поднять до 1440 без изменения кода.
- [Окружение `.venv` проекта ссылается на удалённый Python 3.12] → пересоздать
  перед реализацией, это первая задача.
